### 行为契约（已由单测覆盖）

- `keyActionRouter.test.ts` `"?" opens help modal`：
  `routeKey(state, dispatch, '?', key, opts)` 派发
  `{ type: 'OPEN_MODAL', modal: 'help' }` 单次，与 router L124-125 一致。
- `keyActionRouter.test.ts` `non-confirm modals short-circuit letter keys` 第 4 例
  `modal === 'help'`：在 help 模态期间 `r`/`n`/`a`/`c` 全部 no-op，
  router **不**派发任何 action（router L86 提前 return；HelpModal 自身
  没有 useInput 接收这些字母键）。
- `App.test.ts` "defaults modalContext to {} when ctx is omitted"：
  `reducer(state, { type: 'OPEN_MODAL', modal: 'help' })` → `state.modal === 'help'`、
  `state.modalContext` 为 `{}`（OPEN_MODAL 不带 ctx 时默认空对象的契约）。
- `App.test.ts` "replaces any prior modal/context atomically"：
  rename → help，rename 的 ctx（renameKind/renameId/renameCurrentName）
  被完全替换为 `{}`——帮助是只读展示，不依赖任何 modal 字段。
- `App.test.ts` "search takes over from help"：help → search 也可正常
  替换，证明 help 模态不会阻断其它 OPEN_MODAL action（router 不会主动
  在 help 状态下吞掉所有 key，但字母键在 modal !== 'none' 分支被
  router L86 短路）。
- `App.test.ts` "Action union exhaustiveness"：`OPEN_MODAL modal: 'help'`
  在 reducer 中走 `case 'OPEN_MODAL'` 分支，不抛错。

- [ ] **Step 3：按 `?`，观察 HelpModal 弹出**

  在主视图（任意焦点均可，焦点不影响 `?`）按 `?`。

  期望：
  - **模态框架**：青色（cyan）边框的圆角矩形浮层，居中叠加在两栏之上，
    不替换主视图内容（这是与 `settings` / `rename` 等同样挂在 App render
    末尾的 overlay 行为）。
  - **标题**：顶部加粗 `Keyboard shortcuts`。
  - **键位列表**：12 行 cyan 色 key + 灰色描述，从上到下依次为：

    | key | description |
    |-----|-------------|
    | `Tab` | Switch pane |
    | `↑ / ↓` | Navigate |
    | `Enter` | Resume session |
    | `n` | New session in project |
    | `r` | Rename focused item |
    | `d` | Delete manual project |
    | `c` | Copy session ID |
    | `/` | Search sessions |
    | `a` | Add manual project |
    | `,` | Open settings |
    | `?` | Show this help |
    | `q / Ctrl+C` | Quit |

    键盘名一栏宽度对齐（`padEnd(12)`），每个 key 段为 cyan，描述段为默认色。
  - **底部副标题**：`Press ? or Esc to close`（`dimColor` 灰色提示）。

- [ ] **Step 4：把 HelpModal 留在屏上，按其它键位验证 help 内不被穿透**

  仍然在 help 模态下，按以下键：

  - `r`、`n`、`a`、`c`：不应触发 rename / new session / add project /
    copy ID；模态不消失（router L86 + 模态吞字测试间接守住）。
  - `Tab`：模态不消失（`useKeybindings` 派发 `TOGGLE_FOCUS`，但 help
    模态是纯展示层，模态外的 project / session 高亮变化**正常**——只有
    modal 叠加不会吸收 Tab）。
  - `↑` / `↓`：会被 `useKeybindings` 派发到 `onUp` / `onDown`，但
    App.tsx L201-202 的 `onUp` / `onDown` 是 `() => {}` no-op，故肉眼上
    看不到变化（侧栏 focus 不会移动）。
  - `q` / `Ctrl+C`：⚠️ 当前 `q`/`Ctrl+C` 仍由 router L109 调用 `opts.onQuit()`
    退出进程；help 模态不挡 quit。**真实 GUI 中按 `q` 会**直接退出 ccsm，
    所以帮组开屏时不要按 `q`。

  期望（除 `q` 外）：模态保持，所有其它字母 / 方向键不穿透。

- [ ] **Step 5：再按一次 `?` 关闭（⚠️ 已知 limitation）**

  在 help 模态仍在屏上的状态下，按 `?`。

  期望（按 brief Step 1「再次 `?` 关闭」）：
  - HelpModal 关闭，回到主视图（`modal === 'none'`）。

  ⚠️ **当前代码不会发生**：`routeKey` 在 `state.modal !== 'none'` 时
  直接 `return`（router L86），所以 `?` 字符根本不会走到 L124-125 的
  分支派发 `OPEN_MODAL`。HelpModal 内部**也没有**自己的 `useInput`、
  **没有** `useEscapeToCancel`，所以按 `?` 不会有任何反应——HelpModal
  仍在屏上。

  实装位置建议（不在本任务范围）：
  - 方案 A（推荐）：HelpModal 内增加 `useEscapeToCancel` 风格的处理：
    ```tsx
    import { useInput } from 'ink';
    // HelpModal.tsx 组件内
    useInput((input) => {
      if (input === '?' || input === 'q' /* 防止误关 */) onClose();
    });
    ```
    但需小心 `q` 也接管——往往 help 里只想接 `?` 和 Esc。把 `q` 留给
    router 的 `onQuit` 是合理分工。
  - 方案 B：在 router 的 main-view `?` 分支前加 `if (state.modal === 'help') { dispatch CLOSE_MODAL; return; }`。

## Step 2 已知 limitation（重要）

### Limitation 1：HelpModal 没有 `?` toggle / Esc 关闭的实装

**当前实装的 `?` 路径**：
- `keyActionRouter.ts` L124-125：仅处理 `state.modal === 'none'` 时的 `?`。
- `src/tui/modals/HelpModal.tsx` 组件内部**没有** `useInput`、`useEscapeToCancel`。
- 组件 props `onClose` 在 `App.tsx` L342 挂到 `CLOSE_MODAL` 派发，但目前
  **没有任何按键**会触发 `onClose`——它只是个**未来 hotfix 占位符**，
  与 HelpModal 自家 L24-26 的注释：「`onClose is wired in a follow-up
  task (Esc handling in useKeybindings / App)`」吻合。
- `src/tui/hooks/useKeybindings.ts` L48 全局 Esc 路由到
  `cbs.onClearSearch()`，但 App.tsx L203 该回调是 `() => {}` no-op，
  不会触发 `CLOSE_MODAL`。

**HelpModal L35 提示文案 `Press ? or Esc to close` 与实现脱节**——属于契约
gap，由 hotfix/tweak task 推进补：
1. 在 `HelpModal` 加 `useEscapeToCancel(onClose)`（最快），或
2. 在 `HelpModal` 加自挂的 `useInput` 同时支持 `?` 和 Esc，或
3. 在 `keyActionRouter.ts` main-view 分支前针对 `modal === 'help'` 加
   `?` 分支（与 router L86 提前 return 互斥，需要重排）。

**任一方案都要补两类回归**：
- 单测：覆盖 HelpModal 关闭路径——例如 `tests/tui/keyActionRouter.test.ts`
  新增 `"?" closes help modal when modal === 'help'` 1 例 +
  `"Esc closes help modal when modal === 'help'` 1 例；如果方案 1 在
  HelpModal 内挂 `useEscapeToCancel`，则补 `tests/tui/modals/HelpModal.test.ts`
  配合 `tests/tui/hooks/useEscapeToCancel.test.ts` 模式。
- 同步更新 HelpModal 副标题文案或将其降级为「按 Esc 关闭」（关闭真发生后
  字符才为真），避免继续误导用户。

### Limitation 2：help 期间其它键盘事件有局部副作用

- `q` / `Ctrl+C` 在 help 期间仍能 quit（router L109 不区分 modal）。
  是 design choice：用户遭遇不可恢复状态时需要能硬退出。**真实测试时
  help 里按 `q` 会退出 ccsm，请勿在 help 屏按 `q`**。
- `Tab` 在 help 期间正常派发 `TOGGLE_FOCUS`（App.tsx L188-204 的
  `useKeybindings` 不感知 modal），侧栏 focus 高亮会变。这是无害的
  UX 副作用，可后续考虑在 modal 期间抑制。
- `↑` / `↓` 在 help 期间被 `useKeybindings` 派发到 `onUp` / `onDown`，
  但 App 端该 callback 是 `() => {}` no-op，侧栏不滚动。

### Limitation 3：esc-to-close 候选与 router `Esc in confirm` 的相互影响

如果按方案 1 / 3 实装 Esc 关闭 help，需要在 `keyActionRouter.ts` 中
**先匹配 Esc，再判 modal**：
```ts
if (key.escape) {
  if (state.modal === 'confirm' || state.modal === 'help') {
    dispatch({ type: 'CLOSE_MODAL' });
    return;
  }
  // 主视图 Esc 仍留给 Task 9.6 的 clear-search 逻辑
}
```
否则当前的 confirm Esc 分支（L77-80）会被绕过。务必同步 Task 9.6
的 Esc-in-main-view clear-search 实现（它和 help Esc 同根）。
